# План реальных E2E-проверок v1

## Принцип

Полный игровой E2E считается реальным только при запуске production-бинарников
и подключении к настоящим внешним системам. Заглушки LM Studio, OCR, WinAPI,
игрового окна, кадров, цен и действий мыши в полном прогоне запрещены.

Отдельный transport E2E проверяет только процессный жизненный цикл и WebSocket
между настоящими бинарниками `controller` и `windows-agent`. Он намеренно
работает в `PAUSED`, не вызывает LM Studio/OCR и не является доказательством
работы наблюдения или торговли.

Скриншоты не заменяют системный тест с запущенной игрой. Они используются для
повторяемых регрессионных проверок распознавания только после получения права на
их хранение и фиксации версии клиента, разрешения, DPI, языка и SHA-256 каждого
файла. Синтетически отрисованный интерфейс не считается доказательством работы
с Arena Breakout Infinite.

## Предварительные условия полного прогона

- Windows-машина с поддерживаемой версией Arena Breakout Infinite;
- тестовая учётная запись и разрешение правообладателя на автоматизированный ввод;
- отдельный бюджет и предметы, потеря которых допустима;
- WSL с production-сборкой `controller`, LM Studio, OCR и SQL-базой;
- зафиксированные разрешение, DPI, язык интерфейса и версия игры;
- обязательные положительные `ARENA_EXPECTED_WIDTH`,
  `ARENA_EXPECTED_HEIGHT` и `ARENA_EXPECTED_DPI`, измеренные для client area;
- разрешённый набор реальных скриншотов всех заявленных состояний;
- аппаратная аварийная остановка и запись экрана всего прогона.

Без этих условий нельзя честно заявлять о проверке игровых сценариев.

## Матрица сценариев

### Транспорт и жизненный цикл

1. Контроллер запускается и отвечает на `/healthz`.
2. Реальный бинарник агента подключается, отправляет `HELLO` и виден в health.
3. Heartbeat сохраняет соединение дольше тайм-аута.
4. Штатная остановка агента удаляет его из состояния контроллера.
5. Потеря агента немедленно останавливает торговую сессию.
6. Повторное подключение после перезапуска восстанавливает наблюдение, но не
   продолжает денежный шаг без reconciliation.

Первые четыре пункта покрывает автоматический тест
`./scripts/docker-go.sh go test -p=1 -tags=e2e ./tests/e2e`. Он собирает и
запускает настоящие бинарники как отдельные процессы внутри ограниченного
контейнера. Controller получает абсолютный путь runtime-конфигурации, временные
SQLite/recordings и временный рабочий каталог. Поэтому тест не пишет в
`data/`, не использует установленную модель и не обращается к LM Studio/OCR.
Локальные URL вычислительных сервисов заведомо не слушаются; переходы в
preflight/observe тест не выполняет. Оба процесса завершаются через SIGTERM и
обязательный cleanup даже после раннего падения проверки.

Ограничения transport E2E: 1024 MiB памяти без swap, один CPU, 128 PID,
отключённая сеть контейнера и последовательная Go-сборка `-p=1`.

### Preflight

Проверяются доступность LM Studio и OCR, окно и foreground игры, client area,
DPI, разрешение, текущий экран, баланс, инвентарь, рыночные слоты и риск-лимиты.
Каждый отказ проверяется отдельно: режим `TRADE` не должен запускаться.

### Наблюдение по реальным кадрам

Для каждого `ScreenState` проверяются классификация, ROI, OCR денежных значений,
bounding box элементов и confidence. Дополнительно проверяются неизвестный
экран, диалог ошибки, перекрытие окна, изменение разрешения, масштабирование,
локализация и расхождение двух чтений OCR. Артефакт проверки включает исходный
кадр, нормализованное наблюдение и журнал решения.

### Навигация и безопасность ввода

Проверяются все рёбра графа экранов, повтор действия, просроченная команда,
устаревший `BasedOnFrame`, несовпавший `ExpectedState`, потеря foreground,
сворачивание игры, движение мыши пользователем и emergency stop. Отдельно
подтверждается, что ввод выполняет только один последовательный executor.

### Экономика и риск

На фактических карточках рынка проверяются цена покупки, комиссия, listing fee,
чистая выручка, прибыль, ROI, свежесть котировки и лимит единичной цены. На
фактических рецептах проверяются количества ингредиентов, cooldown, доступность,
занимаемые слоты и многоступенчатая стоимость. Любое расхождение OCR блокирует
денежное действие.

### Торговая saga и recovery

Основной путь: купить ингредиенты, подтвердить инвентарь, выполнить обмен,
подтвердить результат, выставить его и подтвердить активный ордер. Отдельные
прогоны создают реальные контролируемые отказы: A не куплен; A куплен, B
недоступен; A и B куплены, обмен на cooldown; обмен завершён, рынок недоступен;
рыночные слоты закончились; цена изменилась перед подтверждением. После каждого
денежного шага сверяются кадры до и после, баланс, инвентарь и запись в БД.

### Приёмочный прогон

Фиксированный маршрут из ТЗ выполняется 50 раз подряд. Результат принимается
только при нуле ошибочных покупок, потерянных действий и нераспознанных денежных
значений, при 100% recovery и наличии журнала каждого действия. Отчёт должен
содержать версии всех компонентов, хеши кадров, логи, записи БД и видеозапись.

После остановки торговой сессии машинно-проверяемая часть отчёта строится из
неизменяемого журнала controller:

```bash
./acceptance-report \
  -db data/arena.db \
  -runs 50 \
  -opportunity fixed-route-id \
  -since 2026-07-30T08:00:00Z \
  > acceptance-report.json
```

`-opportunity` и `-since` необязательны. `-opportunity` задаёт ожидаемую
фиксированную возможность, но не скрывает прогоны другого маршрута фильтром:
любой такой прогон среди последних 50 отклоняет отчёт. Без флага фиксированный
идентификатор выводится из первого выбранного прогона. Команда печатает JSON и
завершается с ненулевым кодом, если последние 50 последовательных снимков
исполнений не проходят критерии. Проверяются строгий статус `SagaCompleted`,
точная reconciliation, порядок `BUY… → BARTER → LIST → SALE_SETTLED`, 100%
завершённых recovery, точные `MonetaryActionID` из checkpoint, отсутствие
посторонних денежных действий, полные основания и контрольные кадры команд,
успешные `PURCHASE`/`BARTER`/`LISTING`, отсутствие аварийных/критических событий
и переполнения ограниченного аудитора (не более 10 000 действий на прогон).
Команду следует запускать на остановленной сессии, чтобы набор проверяемых
записей не менялся во время постраничного чтения.

## Текущее состояние

В репозитории реализованы transport lifecycle, Windows Window Manager,
adaptive GDI capture, последовательный SendInput executor, safety supervisor,
LM Studio/OCR adapters, SQLite, запись кадров, session coordinator, dashboard,
экономические расчёты, риск, opportunity finder, inventory и reconciliation.
Автоматические Go-тесты и transport E2E не заменяют игровой приёмочный прогон.

Полный торговый маршрут пока нельзя помечать пройденным: нужны калибровка
реальных экранов и OCR ROI для текущей версии игры, проверка каждого ребра
навигации, watchlist/рецепт и лимиты риска, разрешение на автоматизированный
ввод, тестовый бюджет и 50 последовательных реальных повторений. До этого
запуски выполняются без `-allow-input` только в `PAUSED`, `OBSERVE` или
`SIMULATE`.

Вычислительная модель v1 — только `qwen3.5-0.8b` из
`lmstudio-community/Qwen3.5-0.8B-GGUF`, квантовка Q4_K_M с vision projector.
Gemma в runtime и при E2E не используется.
